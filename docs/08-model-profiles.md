# 08. Профили моделей и отказоустойчивость при исчерпании лимитов

Статус: **реализовано (D44–D49)**. Код покрыт unit- и integration-тестами.

## 1. Контекст проблемы

При работе задачи `KINOMAX-INTEGRATION` supervisor завершился ошибкой провайдера:
```text
Error: Codex error: The usage limit has been reached
```
Текущее поведение ядра:
1. Ошибка лимита трактуется как обычный временный сбой сети/сервера: выполняются 2 технических повтора с задержкой 15 секунд (`technicalRetries`, `technicalRetryDelaySeconds`). Лимит за 15 секунд не восстанавливается.
2. После исчерпания повторов задача блокируется с кодом `SUPERVISOR_NO_DECISION`.
3. В расширении блокировка приводит к отвязке задачи от сессии (`/teo stop`), и пользователю приходится вручную разблокировать задачу через `teo recover` и повторно запускать `/teo resume`.

Дополнительно в текущей схеме каждая роль (агент или supervisor) привязана ровно к одной модели (`model: <ref>`). При исчерпании лимита подписки или недоступности модели весь процесс останавливается, даже если у пользователя настроены другие провайдеры (Anthropic Claude, OpenAI Codex, Google Gemini и т. д.).

## 2. Принятые решения

| # | Решение |
|---|---|
| D44 | Ошибки лимитов и квот (`usage limit`, `rate limit`, `insufficient_quota`, HTTP 429) выделяются в отдельный класс ошибок `MODEL_EXHAUSTED`. Они не тратят технические повторы и не блокируют задачу кодом `SUPERVISOR_NO_DECISION` |
| D45 | Общая конфигурация моделей в `~/.pi/teo/models.md`: задаёт списки моделей (fallback chain) по приоритету для ролей и именованных профилей. Файл процесса (`<process>.md`) может переопределять или дополнять профили |
| D46 | Модели в списках задаются ровно так, как они представлены в Pi: по отображаемому имени (`name`), идентификатору (`id`), полному `provider/id` или известным алиасам Pi CLI (например: `GPT-5.5`, `Opus-5.5`, `Gemini Pro 3.1`), с опциональным суффиксом уровня мышления (`:high`, `:low` и т. д.) |
| D47 | Cooldown-трекер моделей: исчерпанная модель помечается временно недоступной до срока сброса. Срок берётся из точной пробы провайдера, иначе из текста ошибки, иначе из нарастающего графика проб (15 мин … 24 ч). Лимит аккаунта закрывает всего провайдера. Cooldown-ы хранятся в `~/.pi/teo/model-cooldowns.json` и снимаются вручную через `teo models reset` |
| D48 | Автоматический fallback: при ошибке лимита или неготовности модели (не найдена / не авторизована) роль переключается на следующую доступную модель из цепочки. В сессии Pi вызывается `pi.setModel` и выводится информационное уведомление о переключении |
| D49 | Исчерпание всех моделей цепочки: supervisor не блокирует задачу, а переходит в фазу `waiting` с обратным отсчётом до сброса лимита (`⏳ ⚠ лимит моделей исчерпан · осталось MM мин SS сек`); дочерний агент этапа прерывает ход и ставит задачу на паузу с явным уведомлением |

## 3. Конфигурация: `~/.pi/teo/models.md`

Файл хранится в `~/.pi/teo/models.md` рядом с файлами процессов. Имеет YAML front matter и markdown-комментарии:

```yaml
---
schema: teo/v1

# Привязка конкретных ролей к цепочкам моделей по приоритету
roles:
  supervisor:
    - GPT-5.5:high
    - Opus-5.5:high
    - default
  explorer:
    - Claude Sonnet 5.5
    - GPT-5.5
    - default
  executor:
    - GPT-5.5:high
    - Opus-5.5:high
    - default

# Именованные профили для переиспользования в процессах
profiles:
  strong:
    - GPT-5.5:high
    - Opus-5.5:high
  fast:
    - Claude Sonnet 5.5
    - GPT-5.5
    - default
---

# Настройки моделей TEO

Список моделей задаётся в порядке приоритета: первая доступная используется в первую очередь.
Имена моделей соответствуют каталогу Pi (показаны в `/models` или `pi --models`).
```

### 3.1. Связь с файлами процессов

В файлах процессов (`~/.pi/teo/<процесс>.md`):
- `agents.<id>.model` и `supervisor.model` могут содержать:
  1. имя профиля из `models.md` (`model: strong`);
  2. одиночную модель по имени Pi (`model: "Opus-5.5:high"`);
  3. список моделей прямо в процессе (`model: [GPT-5.5:high, Opus-5.5:high, default]`);
  4. значение `default` (модель пользовательской сессии Pi).
- Если в процессе указано `model: default`, но для роли в `~/.pi/teo/models.md` задана секция `roles.<agentId>` (или `roles.supervisor`), используется цепочка из `models.md`.

## 4. Разрешение моделей (Pi Model Matching)

Разрешение строки модели опирается на возможности Pi SDK:
1. Выделяется суффикс мышления (например, `:high` из `Opus-5.5:high`).
2. Базовая строка сопоставляется с моделями из `ctx.modelRegistry` / `session.modelRuntime.getAvailableSnapshot()`:
   - точное совпадение по `provider/id` (например, `openai-codex/gpt-5.5`);
   - точное совпадение по `id` без учёта регистра (например, `gpt-5.5`, `claude-opus-5-5`);
   - совпадение по `name` без учёта регистра (например, `GPT-5.5`, `Claude Opus 5.5`, `Gemini Pro 3.1`);
   - fuzzy/prefix совпадение через функции Pi SDK (`resolveCliModel` / `resolveModelReference`).
3. Модель проверяется на наличие авторизации (credentials). Если ключа/токена нет, модель сразу считается недоступной для fallback-цепочки и пропускается с записью в журнал.

## 5. Детектор лимитов и трекер cooldown

### 5.1. Детектор ошибок провайдера
Функция `isModelExhaustedError(err)` определяет:
- ключевые фразы провайдеров в тексте ошибки: `usage limit`, `rate limit`, `insufficient_quota`, `quota exceeded`, `resource_exhausted`, `overloaded`;
- HTTP статус 429.

`exhaustionScope(err)` различает, на что распространяется лимит:
- `provider` — лимит аккаунта или подписки (`usage limit`, `insufficient_quota`, `billing`, `subscription`):
  бессмысленно пробовать другие модели того же провайдера, cooldown ставится на провайдера целиком;
- `model` — короткий rate limit (`429`, `too many requests`, `overloaded`): cooldown только на модель.

### 5.2. Срок сброса
Порядок источников:
1. **Точная проба провайдера** (`EngineCore.providerReset`). Для `openai-codex` — `backend-api/codex/usage`:
   `primary_window` = 5-часовое окно, `secondary_window` = недельное. Если исчерпаны оба, берётся более
   поздний срок. Эндпоинт ненадёжен (бывает 403 через Cloudflare), поэтому проба строго
   опортунистическая: любая ошибка значит «срок неизвестен».
2. **Текст ошибки** (`parseResetCooldownMs`): `retry-after` (секунды, `-ms`, HTTP-date), относительные
   интервалы (`in 14m30s`, `try again in ~45 min`, `in 5 hours`, `in 2 days`, `через 30 минут`),
   абсолютное время (`resets at <ISO>`, `resets_at: <unix>`). Сроки дальше 14 суток отбрасываются.
3. **График проб** (`PROBE_SCHEDULE_MS`), когда срок неизвестен:
   15 мин → 30 мин → 1 ч → 2 ч → 4 ч → 8 ч → 24 ч (крышка). Номер попытки растёт при каждом
   повторном исчерпании и сбрасывается после успешного вызова (`recordSuccess`).
   Проба — это следующая попытка supervisor-а по истечении срока; исчерпанный провайдер отвергает
   запрос до генерации, поэтому проба дешёвая.

Даже для известного долгого срока допускается контролируемая canary-проверка не чаще раза в час,
но только когда все остальные модели цепочки недоступны. Это защищает от устаревшего cooldown
после смены аккаунта или досрочного восстановления лимита. Успех снимает cooldown; повторная
ошибка лимита обновляет его. `claimProbe` бронирует проверку до запроса, чтобы задачи одного
процесса не дублировали canary.

Если срок взят из графика, а не от провайдера, в `wait.resetKnown` пишется `false`, и UI не показывает
выдуманный обратный отсчёт: вместо `до <дата>` выводится `срок сброса не сообщён · проба через …`.

### 5.3. `ModelCooldownTracker`
Запись на провайдера (`modelId: null`) или на модель:
- `exhaustedUntil`, `attempt`, `reason`, `recordedAt`;
- `resetKnown`, `resetDetail` сохраняют семантику срока между перезапусками;
- `lastProbeAt`, `nextProbeAt` управляют контролируемыми canary-проверками;
- `isExhausted(provider, modelId)` — сначала проверяется запись провайдера, затем модели;
- `recordExhausted(provider, modelId, durationMs, reason, now, { scope, resetDetail })` — `durationMs: null` включает график проб;
- `recordSuccess(provider, modelId)` — снять cooldown и сбросить график;
- `canProbe` / `claimProbe` — проверить и атомарно для процесса забронировать canary;
- `list()` и `reset(provider?, modelId?)` — для CLI.

### 5.4. Хранение на диске и ручной сброс
Cooldown-ы переживают перезапуск процесса: `~/.pi/teo/model-cooldowns.json`.
Файл **глобальный, а не в `.teo` проекта**: лимит принадлежит аккаунту провайдера, а не
репозиторию, и несколько проектов должны видеть один и тот же cooldown. Запись атомарная
(tmp + rename, права `0600`), текст ошибки редактируется от секретов, битый файл — не ошибка,
а отсутствие cooldown-ов. Записи старше 7 суток удаляются.

Ручное управление:
```
teo models cooldown [--json]              # активные cooldown-ы, срок и номер пробы
teo models reset <provider>               # снять все записи провайдера
teo models reset <provider>/<model>       # снять запись модели
teo models reset --all                    # снять всё
```

### 5.5. Провайдеры, непригодные для supervisor-а
Сессия supervisor-а создаётся через SDK и **всегда без расширений Pi**
(`noExtensions` для роли supervisor в `pi-agent-runtime.openSession`): supervisor оценивает работу
агентов и не должен зависеть от пользовательских расширений.

Большинству провайдеров это безразлично: они берут системный промпт из контекста запроса
(так работает `pi-antigravity`). Но провайдер может быть реализован как мост, которому нужен
собственный хук внутри вызывающей сессии:

- `claude-bridge` проксирует запрос в Claude Code и проецирует туда системный промпт, записанный
  его хуком `before_agent_start`. Хранилище капч process-global, но наполняют его только сессии,
  где расширение загружено. У сессии supervisor-а расширений нет, капчи для её промпта не
  существует, и мост отказывается работать с ошибкой `prompt-capture: no capture`.
- Для **ролей этапов тот же провайдер работает штатно**: они идут в пользовательской сессии Pi,
  где `before_agent_start` срабатывает.

Узнать это по факту разрешения модели нельзя — модель разрешается и авторизована, а ошибка приходит
только во время хода. Поэтому список таких провайдеров задан явно
(`PROVIDERS_NEEDING_SESSION_EXTENSION` в `src/agents/pi/provider-traits.ts`):
- `selectSupervisorModel` пропускает их без холостой попытки;
- `teo doctor` предупреждает, если такой провайдер стоит в цепочке роли `supervisor`,
  чтобы это не выяснялось блокировкой задачи посреди работы.

Независимо от списка работает общая страховка (§6.1): любая устойчивая ошибка провайдера ведёт
к переходу на следующую модель цепочки, а не к блокировке.

## 6. Алгоритм Fallback

### 6.1. Для Supervisor
1. Supervisor начинает цикл. Из конфигурации роли `supervisor` берётся цепочка моделей.
2. Проверяется каждая позиция цепочки. Результат (`selected`, `cooldown`, `unavailable`,
   `incompatible`, `unusable`, `canary`) вместе с разрешением `default` в фактическую модель
   пишется в событие `supervisor.models_checked`. Выбирается первая доступная модель.
   Смена модели требует переоткрытия сессии: `SessionPool` кеширует сессии по пути файла, и без
   сравнения модели запрос ушёл бы в прежнюю, уже исчерпанную модель. Файл транскрипта при этом
   тот же, история не теряется.
3. Непригодные для роли модели пропускаются сразу: провайдеры-мосты (§5.5) и модели, уже
   упавшие в этом процессе с устойчивой ошибкой провайдера.
4. Если модель завершается с ошибкой лимита:
   - в cooldown заносится только то, что реально ответило ошибкой (модель открытой сессии),
     и в области из `exhaustionScope`: весь провайдер или одна модель;
   - в журнал пишется событие `model.exhausted`;
   - если в цепочке есть следующая доступная модель:
     - пишется событие `supervisor.model_fallback`;
     - цикл повторяется сразу на резервной модели;
   - если доступных моделей нет, сначала рассматривается наступившая canary-проверка cooldown;
   - если canary ещё не разрешена, задача переходит в `waiting` до ближайшей canary или сброса;
   - сообщение ожидания перечисляет каждую модель и причину пропуска. Формулировка «все модели
     исчерпаны» используется только для чистого cooldown; смешанный случай (часть cooldown,
     часть unavailable) называется «нет доступной модели supervisor-а»;
   - при наступлении срока автоматически запускается новая попытка.
5. Если модель завершается другой ошибкой провайдера (не лимит):
   - один вызов модели ограничен `runtime.supervisorModelTimeoutMinutes` (default 10). Watchdog
     прерывает зависший `session.prompt`; timeout считается устойчивой provider error и сразу
     запускает fallback, а не protocol retry. UI показывает elapsed и последний auto-retry;
   - сначала расходуются `technicalRetries` на той же модели — случайный сбой заслуживает повтора;
   - когда повторы исчерпаны, ошибка считается устойчивой: пишется `model.unusable`, модель
     выводится из цепочки до перезапуска процесса, и цикл продолжается на следующей модели;
   - cooldown при этом **не** ставится: это не лимит аккаунта;
   - `SUPERVISOR_NO_DECISION` возникает только когда в цепочке не осталось живых моделей.

### 6.2. Для агентов этапов
1. При входе в этап определяется цепочка моделей роли.
2. Применяется первая доступная модель (в режиме расширения: `await pi.setModel(model)`).
3. Если host-ход Pi завершается ошибкой лимита, extension mode извлекает реальный
   `errorMessage` последнего assistant message, а не сохраняет общий текст runtime error.
4. Если во время хода агента провайдер возвращает ошибку исчерпания лимита:
   - модель заносится в cooldown, а для subscription/account limit — весь провайдер;
   - кеш применённой модели этапа сбрасывается, поэтому следующий continue/recheck выбирает
     следующую доступную модель цепочки;
   - если есть резервная модель: сессия переключается на неё через `pi.setModel`, пользователю выводится `notify: teo: переключение роли «<роль>» на модель <name> (лимит исчерпан)`;
   - если все модели исчерпаны: задача переходит на паузу, в статус выводится `teo: KEY · пауза: лимит моделей роли исчерпан`, пользователю предлагается продолжить позже через `/teo resume`.

## 7. Этапы реализации

План разбит на 3 последовательных шага:

### Шаг F1: Конфигурация и распознавание моделей Pi
- Создание схемы и загрузчика `~/.pi/teo/models.md` (`src/policy/models-config.ts`).
- Расширение валидации `model` в `src/domain/policy.ts` и `src/policy/policy-schema.ts`: поддержка имен Pi, массивов моделей и ссылок на профили.
- Функция разрешения моделей `resolveModelChain(...)` через Pi SDK с поддержкой имен `name`/`id`/`fuzzy`.
- Проверка в `teo doctor`: валидация `models.md` и статуса моделей каждого профиля.
- Тесты: unit-тесты на парсинг, нормализацию, fuzzy-matching по именам из Pi.

### Шаг F2: Детектор лимитов и трекер cooldown
- Модуль `src/util/model-exhaustion.ts`: распознавание 429/quota/rate limit, парсинг reset-интервалов, in-memory трекер.
- Новые события в `src/domain/events.ts`:
  - `model.exhausted: { provider: string; modelId: string; resetAt: string; reason: string }`
  - `model.fallback: { role: string; fromModel: string; toModel: string; reason: string }`
- Тесты: unit-тесты детектора на реальных ошибках OpenAI Codex, Anthropic, Google.

### Шаг F3: Интеграция fallback в Workflow и Расширение Pi
- Модификация `src/workflow/supervisor-step.ts`: перехват `MODEL_EXHAUSTED`, немедленный переход к следующей модели или в `phase=waiting` без блокировки задачи.
- Модификация `src/extension/host.ts` и `src/extension/workflow.ts`:
  - переключение `pi.setModel` при fallback агента этапа;
  - отображение в статус-баре `⏳ ⚠ лимит моделей исчерпан · осталось MM мин SS сек`;
  - таймер автопродолжения при окончании cooldown.
- Integration-тесты в `test/integration/model-profiles.test.ts`:
  - supervisor исчерпал основную модель → автоматически переключился на запасную и завершил проверку;
  - все модели исчерпаны → переход в `waiting` с таймером, восстановление после сброса;
  - дочерний агент переключает модель в сессии Pi.

## 8. Чек-лист приёмки

1. В `~/.pi/teo/models.md` можно задавать профили и роли с именами как в Pi (`GPT-5.5`, `Opus-5.5:high`, `Gemini Pro 3.1`).
2. Ошибка «The usage limit has been reached» больше не блокирует задачу.
3. При наличии запасной модели supervisor прозрачно завершает проверку на ней.
4. В журнале событий фиксируются `model.exhausted` и `model.fallback`.
5. При исчерпании всех моделей задача переходит в ожидание с таймером обратного отсчёта.
6. `npm run check` и e2e тесты полностью зелёные.
