# 08. Профили моделей и отказоустойчивость при исчерпании лимитов

Статус: **реализовано (D44–D49)**. Код покрыт unit- и integration-тестами.

## 1. Контекст проблемы

При работе задачи `KINOMAX-INTEGRATION` supervisor завершился ошибкой провайдера:
```text
Error: Codex error: The usage limit has been reached
```
Текущее поведение ядра:
1. Ошибка лимита трактуется как обычный временный сбой сети/сервера: выполняются 2 технических повтора с задержкой 15 секунд (`technicalRetries`, `technicalRetryDelaySeconds`). Лимит за 15 секунд не восстанавливается.
2. После исчерпания повторов задача блокируется с кодом `SUPERVISOR_NO_DECISION`.
3. В расширении блокировка приводит к отвязке задачи от сессии (`/teo stop`), и пользователю приходится вручную разблокировать задачу через `teo recover` и повторно запускать `/teo resume`.

Дополнительно в текущей схеме каждая роль (агент или supervisor) привязана ровно к одной модели (`model: <ref>`). При исчерпании лимита подписки или недоступности модели весь процесс останавливается, даже если у пользователя настроены другие провайдеры (Anthropic Claude, OpenAI Codex, Google Gemini и т. д.).

## 2. Принятые решения

| # | Решение |
|---|---|
| D44 | Ошибки лимитов и квот (`usage limit`, `rate limit`, `insufficient_quota`, HTTP 429) выделяются в отдельный класс ошибок `MODEL_EXHAUSTED`. Они не тратят технические повторы и не блокируют задачу кодом `SUPERVISOR_NO_DECISION` |
| D45 | Общая конфигурация моделей в `~/.pi/teo/models.md`: задаёт списки моделей (fallback chain) по приоритету для ролей и именованных профилей. Файл процесса (`<process>.md`) может переопределять или дополнять профили |
| D46 | Модели в списках задаются ровно так, как они представлены в Pi: по отображаемому имени (`name`), идентификатору (`id`), полному `provider/id` или известным алиасам Pi CLI (например: `GPT-5.5`, `Opus-5.5`, `Gemini Pro 3.1`), с опциональным суффиксом уровня мышления (`:high`, `:low` и т. д.) |
| D47 | Cooldown-трекер моделей: модель с исчерпанным лимитом помечается временно недоступной до времени сброса (если провайдер указал `retry-after` или `resets in`) либо на 30 минут по умолчанию. При наступлении нового этапа или нового supervisor-цикла сначала проверяется основная модель (если cooldown истёк) |
| D48 | Автоматический fallback: при ошибке лимита или неготовности модели (не найдена / не авторизована) роль переключается на следующую доступную модель из цепочки. В сессии Pi вызывается `pi.setModel` и выводится информационное уведомление о переключении |
| D49 | Исчерпание всех моделей цепочки: supervisor не блокирует задачу, а переходит в фазу `waiting` с обратным отсчётом до сброса лимита (`⏳ ⚠ лимит моделей исчерпан · осталось MM мин SS сек`); дочерний агент этапа прерывает ход и ставит задачу на паузу с явным уведомлением |

## 3. Конфигурация: `~/.pi/teo/models.md`

Файл хранится в `~/.pi/teo/models.md` рядом с файлами процессов. Имеет YAML front matter и markdown-комментарии:

```yaml
---
schema: teo/v1

# Привязка конкретных ролей к цепочкам моделей по приоритету
roles:
  supervisor:
    - GPT-5.5:high
    - Opus-5.5:high
    - default
  explorer:
    - Claude Sonnet 5.5
    - GPT-5.5
    - default
  executor:
    - GPT-5.5:high
    - Opus-5.5:high
    - default

# Именованные профили для переиспользования в процессах
profiles:
  strong:
    - GPT-5.5:high
    - Opus-5.5:high
  fast:
    - Claude Sonnet 5.5
    - GPT-5.5
    - default
---

# Настройки моделей TEO

Список моделей задаётся в порядке приоритета: первая доступная используется в первую очередь.
Имена моделей соответствуют каталогу Pi (показаны в `/models` или `pi --models`).
```

### 3.1. Связь с файлами процессов

В файлах процессов (`~/.pi/teo/<процесс>.md`):
- `agents.<id>.model` и `supervisor.model` могут содержать:
  1. имя профиля из `models.md` (`model: strong`);
  2. одиночную модель по имени Pi (`model: "Opus-5.5:high"`);
  3. список моделей прямо в процессе (`model: [GPT-5.5:high, Opus-5.5:high, default]`);
  4. значение `default` (модель пользовательской сессии Pi).
- Если в процессе указано `model: default`, но для роли в `~/.pi/teo/models.md` задана секция `roles.<agentId>` (или `roles.supervisor`), используется цепочка из `models.md`.

## 4. Разрешение моделей (Pi Model Matching)

Разрешение строки модели опирается на возможности Pi SDK:
1. Выделяется суффикс мышления (например, `:high` из `Opus-5.5:high`).
2. Базовая строка сопоставляется с моделями из `ctx.modelRegistry` / `session.modelRuntime.getAvailableSnapshot()`:
   - точное совпадение по `provider/id` (например, `openai-codex/gpt-5.5`);
   - точное совпадение по `id` без учёта регистра (например, `gpt-5.5`, `claude-opus-5-5`);
   - совпадение по `name` без учёта регистра (например, `GPT-5.5`, `Claude Opus 5.5`, `Gemini Pro 3.1`);
   - fuzzy/prefix совпадение через функции Pi SDK (`resolveCliModel` / `resolveModelReference`).
3. Модель проверяется на наличие авторизации (credentials). Если ключа/токена нет, модель сразу считается недоступной для fallback-цепочки и пропускается с записью в журнал.

## 5. Детектор лимитов и трекер cooldown

### 5.1. Детектор ошибок провайдера
Функция `isModelExhaustedError(err)` определяет:
- ключевые фразы провайдеров в тексте ошибки: `usage limit`, `rate limit`, `insufficient_quota`, `quota exceeded`, `resource_exhausted`, `overloaded`;
- HTTP статус 429;
- извлечение времени сброса:
  - заголовки `retry-after`, `x-ratelimit-reset`;
  - паттерны в тексте: `try again in XmYs`, `resets in X seconds`, `until HH:MM`.
- если время не указано: cooldown по умолчанию = **30 минут**.

### 5.2. `ModelCooldownTracker`
Хранит в памяти процесса состояние для каждой модели `(provider, modelId)`:
- `exhaustedUntil: Date`;
- `reason: string`;
- метод `isExhausted(provider, modelId): boolean`;
- метод `recordExhausted(provider, modelId, durationMs, reason)`.

## 6. Алгоритм Fallback

### 6.1. Для Supervisor
1. Supervisor начинает цикл. Из конфигурации роли `supervisor` берётся цепочка моделей.
2. Выбирается первая модель цепочки, у которой нет активного cooldown и есть авторизация.
3. Если модель завершается с ошибкой `MODEL_EXHAUSTED`:
   - модель заносится в cooldown;
   - в журнал пишется событие `model.exhausted`;
   - если в цепочке есть следующая доступная модель:
     - пишется событие `supervisor.model_fallback`;
     - цикл повторяется сразу на резервной модели;
   - если ВСЕ модели цепочки исчерпаны:
     - вычисляется ближайшее время окончания cooldown среди моделей цепочки;
     - задача переходит в фазу `waiting` до этого времени;
     - в статус-баре отображается: `teo: KEY · ⏳ ⚠ лимит моделей исчерпан · осталось MM мин SS сек`;
     - при наступлении срока автоматически запускается новая попытка с основной модели.

### 6.2. Для агентов этапов
1. При входе в этап определяется цепочка моделей роли.
2. Применяется первая доступная модель (в режиме расширения: `await pi.setModel(model)`).
3. Если во время хода агента провайдер возвращает ошибку исчерпания лимита:
   - модель заносится в cooldown;
   - если есть резервная модель: сессия переключается на неё через `pi.setModel`, пользователю выводится `notify: teo: переключение роли «<роль>» на модель <name> (лимит исчерпан)`;
   - если все модели исчерпаны: задача переходит на паузу, в статус выводится `teo: KEY · пауза: лимит моделей роли исчерпан`, пользователю предлагается продолжить позже через `/teo resume`.

## 7. Этапы реализации

План разбит на 3 последовательных шага:

### Шаг F1: Конфигурация и распознавание моделей Pi
- Создание схемы и загрузчика `~/.pi/teo/models.md` (`src/policy/models-config.ts`).
- Расширение валидации `model` в `src/domain/policy.ts` и `src/policy/policy-schema.ts`: поддержка имен Pi, массивов моделей и ссылок на профили.
- Функция разрешения моделей `resolveModelChain(...)` через Pi SDK с поддержкой имен `name`/`id`/`fuzzy`.
- Проверка в `teo doctor`: валидация `models.md` и статуса моделей каждого профиля.
- Тесты: unit-тесты на парсинг, нормализацию, fuzzy-matching по именам из Pi.

### Шаг F2: Детектор лимитов и трекер cooldown
- Модуль `src/util/model-exhaustion.ts`: распознавание 429/quota/rate limit, парсинг reset-интервалов, in-memory трекер.
- Новые события в `src/domain/events.ts`:
  - `model.exhausted: { provider: string; modelId: string; resetAt: string; reason: string }`
  - `model.fallback: { role: string; fromModel: string; toModel: string; reason: string }`
- Тесты: unit-тесты детектора на реальных ошибках OpenAI Codex, Anthropic, Google.

### Шаг F3: Интеграция fallback в Workflow и Расширение Pi
- Модификация `src/workflow/supervisor-step.ts`: перехват `MODEL_EXHAUSTED`, немедленный переход к следующей модели или в `phase=waiting` без блокировки задачи.
- Модификация `src/extension/host.ts` и `src/extension/workflow.ts`:
  - переключение `pi.setModel` при fallback агента этапа;
  - отображение в статус-баре `⏳ ⚠ лимит моделей исчерпан · осталось MM мин SS сек`;
  - таймер автопродолжения при окончании cooldown.
- Integration-тесты в `test/integration/model-profiles.test.ts`:
  - supervisor исчерпал основную модель → автоматически переключился на запасную и завершил проверку;
  - все модели исчерпаны → переход в `waiting` с таймером, восстановление после сброса;
  - дочерний агент переключает модель в сессии Pi.

## 8. Чек-лист приёмки

1. В `~/.pi/teo/models.md` можно задавать профили и роли с именами как в Pi (`GPT-5.5`, `Opus-5.5:high`, `Gemini Pro 3.1`).
2. Ошибка «The usage limit has been reached» больше не блокирует задачу.
3. При наличии запасной модели supervisor прозрачно завершает проверку на ней.
4. В журнале событий фиксируются `model.exhausted` и `model.fallback`.
5. При исчерпании всех моделей задача переходит в ожидание с таймером обратного отсчёта.
6. `npm run check` и e2e тесты полностью зелёные.
