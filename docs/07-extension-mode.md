## 2. Переименование (R1)

Механическая замена, поведение не меняется:

- `package.json`: `name`, `bin: { teo }`, описание; `tsup`: `__TEO_VERSION__`;
- `.sdlc/` → `.teo/` (layout, `.gitignore`, тексты ошибок, тесты);
- `sdlc/v1` → `teo/v1` в загрузчике, фикстурах, `examples/`, документации;
- маркер промптов, `SDLC_FAULT`/`SDLC_E2E`/`SDLC_DEV_*` → `TEO_*`;
- тексты интерфейса: «SDLC Controller» → «Pi Supervisor TEO», подсказки `sdlc …` → `teo …`;
- Docker-образ и volume: `pi-supervisor-teo-dev`, `pi-supervisor-teo-node-modules`, `pi-supervisor-teo-npm-cache` (после переименования один раз `scripts/dev.sh npm ci`);
- `docs/` и README: новые имена. `SDLC_CLI_SPEC.md` остаётся как исторический исходник;
- каталог проекта переносится последним шагом, после зелёного `npm run check`.

Миграции `.sdlc/` → `.teo/` нет: продуктивных задач ещё нет.

## 3. Несколько процессов (R2)

- **Каталог процессов** — `~/.pi/teo/*.md`. Имя процесса — имя файла без `.md`, правила как у ключа задачи, но в нижнем регистре: `car-selection`, `dev`.
- **Задача помнит процесс.** В `state.json` добавляется поле `process`, в `task.created` — тоже. Hash и снимки Policy работают как сейчас, но для файла процесса задачи.
- **Выбор при создании:** `teo new [KEY] --process <имя>`. В терминале без флага — меню выбора; если процесс один, он выбирается сам. Без терминала флаг обязателен, если процессов больше одного.
- **Preflight** проверяет нужный процесс, а не один глобальный файл:
  - `new` — выбранный процесс;
  - команды над задачей (`resume`, `status KEY`, `history KEY`, `cancel`, `recover`) — процесс задачи;
  - сводные (`teo`, `status`, `history`) проверяют все процессы. Задачи процесса с ошибкой Policy помечаются ⚠, остальные работают (D41);
  - `doctor` проверяет каждый процесс отдельной строкой.
- **Нет ни одного процесса** → exit `2` с подсказкой `cp examples/processes/dev.md ~/.pi/teo/dev.md`.
- **Файл процесса задачи удалён** → exit `2` для этой задачи: «процесс X не найден». Задача не меняется.
- **Меню** показывает колонку процесса, шапка — список процессов.
- `examples/SDLC.md` → `examples/processes/dev.md`, `examples/car-selection/SDLC.md` → `examples/processes/car-selection.md`.

## 4. Режим расширения Pi (X1–X5)

### 4.1. Что проверено прототипом

`test/e2e/spike-extension-host.test.ts`, реальная модель, Pi 1.4.0:

| Проверка | Результат |
|---|---|
| Роль этапа через секцию `systemPromptOptions.sections` в `before_agent_start` | ✓ модель следует роли; в той же сессии роль меняется со следующего хода |
| `pi.setActiveTools()` в `before_agent_start` | ✓ набор инструментов этапа уходит провайдеру в том же ходе. Включаются только зарегистрированные инструменты |
| Вложенная сессия supervisor-а внутри `agent_before_settle` | ✓ работает, не мешает основной |
| `agent_before_settle` → `custom_message` + `continue: true` | ✓ агент получил замечание и выполнил его в том же ходе, не возвращая ход пользователю |
| Контекст прошлых этапов в одной сессии | ⚠ «протекает»: агент повторил замечание прошлого этапа. Передачу между этапами нужно формулировать явно |
| Замена сессии из обработчика события | ✗ запрещено документацией: `newSession`/`switchSession` только из команд, иначе возможна взаимоблокировка |

### 4.2. Как это выглядит для пользователя

```text
$ pi                                   # обычная сессия Pi в проекте
> /teo                                 # меню: новая задача / продолжить / цель / статус
> /teo start CAR-1                     # выбор процесса, название и описание — нативные диалоги Pi
  teo: CAR-1 · Выбор типа двигателя · Консультант 1 · цикл 0      ← строка статуса Pi
> Мне нужна машина для города, заряжаться могу дома               ← обычный диалог
  … агент спрашивает, пользователь отвечает …
  ⠋ supervisor проверяет результат                                 ← виджет во время проверки
  ═══ ✓ Выбор типа двигателя → Выбор марки ═══                     ← custom_message в ленте
  … дальше говорит «Консультант 2» в той же сессии …
> /teo status | /teo pause | /teo stop
```

### 4.3. Устройство

Новый слой `src/extension/` — `ExtensionHost`. Он сопоставляет события Pi с фазами существующего движка. Ядро — Policy, decision validator, guards, evidence, журнал `.teo/`, lock, recovery, промпты supervisor-а, redaction — используется без изменений. Изоляция Pi SDK сохраняется: SDK импортируется только в `src/agents/pi/` и `src/extension/`.

| Фаза движка | Событие Pi в режиме расширения |
|---|---|
| `agent_pending → agent_running` | `before_agent_start` пользовательского хода: секция `teo_stage` (роль, инструкции этапа, допустимые переходы, передача), `setActiveTools` по Policy, `pi.setModel` по D38 |
| ход агента | обычный ход пользовательской сессии; файл сессии — сессия Pi пользователя |
| settle | `agent_before_settle`; отчёт — инструменты `report_result`/`report_blocker` (`pi.registerTool`), без отчёта — `unstructured_settle` |
| `supervisor_running` | там же: отдельная сессия supervisor-а в `.teo/tasks/<KEY>/sessions/supervisor.jsonl`, только чтение — как сейчас |
| `decision_pending → apply` | там же, затем эффект в сессии (§4.4) |
| ответ человека | событие `input`: каждое сообщение пользователя при активной задаче пишется как `human.responded` (requestId = null или id открытого вопроса). Это доказательство для guard `humanResponse` |
| прерывание (D42) | Esc → `agent_settled { aborted }` → `runtime.interrupted`, `status = interrupted`; supervision не выключается. Следующий ход (сообщение пользователя или `/teo resume`) начинается с recovery по таблице 03-engine.md §8.3: прерванный run закрывается с `interrupted`, supervisor в ближайшей проверке получает описание прерванного хода и висящих tool calls. `session_shutdown` (Pi закрыт) — тоже прерывание, lock освобождается |
| пауза и выключение | только явно: `/teo pause` — проверки не выполняются, задача и lock остаются за сессией до `/teo resume`; `/teo stop` — supervision выключена, lock освобождён, задачу продолжит `/teo resume` или `teo resume` |

Привязка задачи к сессии:
- в `state.json` — путь файла сессии Pi;
- в сессии — `pi.appendEntry("teo-binding", { key })`, чтобы после перезапуска Pi `session_start` предложил продолжить задачу.

Пока задача активна в расширении, lock проекта держит процесс Pi (heartbeat как в CLI). `teo resume` из терминала в это время получает exit `3`.

`ask_user` в режиме расширения не регистрируется: человек и так в диалоге. Для `read_agent_transcript` каждый logical run получает redacted-снимок новых сообщений host-сессии в `sessions/host-*.jsonl`; исходный файл сессии Pi не копируется целиком.

### 4.4. Решения supervisor-а

| Решение | Эффект в пользовательской сессии |
|---|---|
| `continue_current_agent` | `custom_message` с замечанием + `continue: true`. Повтор ограничен `maxCyclesPerStage` |
| `restart_current_agent` | одна сессия: замечание «начни этап заново» + `continue`; этап с новой сессией — как переход на новую сессию |
| `transition_stage`, этап `userSession: same` (по умолчанию) | баннер перехода + передача (handoff) с явным «предыдущая роль завершена» + `continue: true`: роль нового этапа начинает сама (критерий 13) |
| `transition_stage`, этап `userSession: new` | баннер, `ctx.ui.setEditorText("/teo next")` и подсказка «Enter — начать этап в новой сессии». `/teo next` → `ctx.newSession({ parentSession })` и initial prompt этапа |
| `ask_human` | нативный `ctx.ui.select` (есть варианты) или `ctx.ui.editor` (свободный ответ) прямо в `agent_before_settle` (D39); ответ → `human.responded`, цикл supervisor-а продолжается |
| `schedule_recheck` | статус «ожидание до 15:40». Таймер расширения в срок отправляет prompt перепроверки, если сессия свободна. Если Pi закрыт, продолжит `teo resume` |
| `block_task` / `cancel_task` / терминальный этап | уведомление и виджет с итогом; supervision выключается, lock освобождается |

Новое поле Policy у этапа: `userSession: same | new`, по умолчанию `same`. В CLI-режиме оно игнорируется. Существующее `session: fresh | reuse` по-прежнему управляет сессиями агентов в CLI.

### 4.5. Команды `/teo`

`/teo` (меню), `/teo start [KEY]`, `/teo resume KEY`, `/teo goal <цель>`, `/teo next`, `/teo status`, `/teo pause`, `/teo stop`, `/teo recover KEY`.

`status`, `history` и `cancel` переиспользуют тексты CLI и выводятся через `ctx.ui.notify`/виджет.

### 4.6. Пакет и установка

- Один npm-пакет `pi-supervisor-teo`:
  - `bin: { teo: dist/cli.js }`;
  - `pi: { extensions: ["./dist/extension.js"] }`.
- Расширение собирается отдельной точкой входа tsup в самодостаточный `dist/extension.js`. `@earendil-works/*` и `typebox` — внешние, их подставляет Pi. Остальное (zod, yaml, ulid) вшито: локальный пакет Pi не устанавливает его зависимости. Ink и React в бандл не попадают — это проверяет тест и правило lint: Ink-интерфейс подключается только в `cli.ts`, а `app.ts` и `commands/` его не импортируют.
- Pi SDK и `typebox` — в `peerDependencies: "*"` и в `devDependencies` (точная версия 1.4.0) для сборки, тестов и CLI. Поэтому `npm ci` для CLI — без `--omit=dev`.
- **S6 проверен** (`test/integration/extension-load.test.ts`): с SDK в `dependencies` загрузчик Pi выдаёт предупреждение «Host-provided extension packages must be declared in peerDependencies…». С `peerDependencies` пакет грузится без ошибок и предупреждений и регистрирует `/teo`. Отдельный каталог `extension/` не нужен.
- В print-режиме (`pi -p "/teo status"`) интерфейса нет: ответ `/teo` пишется в stderr, stdout Pi оставляет под ответ модели (`output-guard`).
- Установка: `pi install ~/code/pi-supervisor-teo`. Для пробы без установки: `pi -e ~/code/pi-supervisor-teo`.

## 5. Режим цели (G1)

- `/teo goal <текст>` и `teo new KEY --goal "<текст>"` — задача без выбора процесса, как `/supervise <outcome>` у pi-supervisor.
- Под капотом — встроенный процесс `processes/goal.md` в пакете: файл, а не код. Так критерий 2 («нет процесса в исходниках») соблюдается; литералы файла входят в проверку `no-process-literals`.
  - Один рабочий этап `pursuit` «Достижение цели», агент `performer`; инструкции агента и supervisor-а — общие, сама цель — в описании задачи.
  - Переход в терминальный этап `reached` «Цель достигнута»: `evidence: required`, `humanResponse: optional`.
- Текст цели — описание задачи. Название по умолчанию — первая непустая строка цели (до 200 символов), `--title` его заменяет. `--goal` нельзя сочетать с `--process`, `--description`, `--description-file`.
- В терминале «Цель — без процесса» — пункт выбора процесса в форме. Сначала спрашивается цель, затем название с подсказкой из неё.
- Свой `~/.pi/teo/goal.md` заменяет встроенный шаблон.
- В меню и `status` такая задача показывается с процессом `goal`, в шапке меню — «goal (встроенный)».
- **Без своих процессов** (уточнение D41, G1): если в `~/.pi/teo/` нет ни одного файла, это не ошибка конфигурации — работает режим цели. Exit `2` с подсказкой про `--goal` даёт только `teo new` без `--goal`. Если свои процессы есть, но все невалидны, по-прежнему exit `2` для всех команд: сломанный файл процесса молча не пропускается.

## 7. Риски

- **Пользователь может всё.** Он пишет агенту что угодно и может сам менять файлы. Supervisor управляет только этапом задачи. Guards остаются механической границей для переходов, а не для действий человека.
- **Рост контекста в одной сессии.** Стоит опереться на compaction Pi, а длинные этапы помечать `userSession: new`.
- **Задержка конца хода.** Проверка supervisor-ом занимает 10–30 с, пока работает виджет «supervisor проверяет». Ввод пользователя в это время ставится в очередь Pi.
- **Секреты в журнале (следствие D40)** закрыты D43: свободные сообщения чата проходят redaction.
- **API расширений Pi** развивается быстрее SDK-ядра. Версия Pi закреплена, а прототип e2e остаётся регрессионным тестом допущений.
