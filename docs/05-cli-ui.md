# 05. Команды, интерфейс, exit codes

Детализирует разделы 10, 20, 23, 25 [SDLC_CLI_SPEC.md](../SDLC_CLI_SPEC.md).

## 1. Общие правила

- Все команды, кроме `doctor`, начинаются с preflight Policy ([01-policy.md](01-policy.md#12-последовательность-preflight)). Ошибка → exit `2` до любых других действий.
- `doctor` выполняет preflight как одну из проверок, печатает отчёт и всё равно завершается с `2`, если Policy невалидна.
- Project root определяется до preflight (это только чтение), а показывается в шапке.
- Глобальные флаги: `--no-color`, `--plain` (принудительный линейный вывод даже в TTY), `--json` (для `status` и `history`), `-v/--verbose` (debug-лог в stderr).
- Тексты интерфейса — из каталога сообщений `src/ui/messages.ts`; язык по умолчанию — русский. Тексты из Policy (названия этапов, вопросы) выводятся как есть.

## 2. Команды

| Команда | Lock | Назначение |
|---|---|---|
| `teo` | при выборе действия | Интерактивное меню (основной интерфейс) |
| `teo new [KEY] [--process P \| --goal G] [--title T] [--description-file F \| --description -]` | да | Создать задачу и сразу запустить workflow. Процесс: `--process`, меню в терминале (свои процессы и «Цель»), без терминала единственный свой — сам. `--goal` — режим цели: встроенный процесс, цель — описание, название — её первая строка. Недостающие поля спрашиваются интерактивно; без TTY все поля обязательны, `--process` — если процессов несколько |
| `teo resume <KEY> [--now] [--no-wait]` | да | Продолжить задачу с сохранённой фазы. Для задачи в ожидании: `--now` — перепроверить сразу, `--no-wait` — выйти с exit `6`, если срок не наступил ([03-engine.md §12](03-engine.md#12-отложенная-перепроверка)) |
| `teo status [KEY] [--json]` | нет | Состояние одной задачи, без KEY — сводка по всем |
| `teo history [KEY] [--all] [--json] [--limit N]` | нет | Без KEY — все задачи проекта, включая завершённые; с KEY — лента событий задачи |
| `teo cancel <KEY> [--reason R]` | да | Отмена задачи пользователем, с подтверждением |
| `teo recover <KEY> [--set-stage S] [--accept-policy]` | да | Ручное восстановление: выбор этапа, принятие новой Policy в режиме `pinned`, разбор неоднозначных состояний |
| `teo doctor [--fix]` | для `--fix` | Диагностика; `--fix` предлагает исправления по одному с подтверждением |

`history` в исходной спецификации был без аргументов и без описания; здесь он покрывает и список завершённых задач, и журнал одной задачи. Команды `cancel` и `recover` добавлены: исходная спецификация ссылалась на «команду восстановления» и «явное пользовательское решение» об отмене, но не определяла их.

<a id="teo-recover"></a>

### 2.1. `teo recover`

Интерактивно показывает state, последние события и предлагает только допустимые для ситуации действия:

| Ситуация | Варианты |
|---|---|
| `POLICY_STAGE_MISSING` | выбрать нетерминальный этап новой Policy → `stage.transitioned { by: "human", reason: "manual recovery" }`, `phase = agent_pending { kind: initial }` |
| Policy `pinned` и hash изменился | принять новую Policy (`policy.changed { mode: "manual" }`) |
| `STATE_TAMPERED` | принять текущий файл как есть (после показа diff) или восстановить из последнего `outbox` / журнала |
| Неоднозначный run ([03-engine.md §8.4](03-engine.md#84-неоднозначные-случаи)) | restart / передать supervisor / заблокировать |

Флаги `--set-stage` и `--accept-policy` позволяют сделать то же без меню.

## 3. Главное меню

```text
$ teo

Pi Supervisor TEO
Проект: /Users/user/Projects/cms
Процессы: car-selection (5 этапов), dev (8 этапов)
Каталог процессов: ~/.pi/teo

Что вы хотите сделать?

❯ Создать новую задачу
  PAY-142   dev             Ревью                          ● агент работает (PID 18432)   Добавить оплату через СБП
  AUTH-77   dev             Ожидание подтверждения плана   ? ждёт ответа                  Исправить refresh token
  CRM-12    dev             Код-ревью                      ⏳ перепроверка в 15:40         Экспорт заказов в CSV
  CAR-1     car-selection   Выбор марки                    ○ ждёт запуска агента          Подбор автомобиля
  OLD-3     dev             ⚠ этап «staging» отсутствует в Policy                         Старая задача
  Показать завершённые задачи (4)
  Выход
```

- Колонка процесса — `state.process`. Колонка этапа — `workflow.stages[stage].title` из Policy процесса задачи. Если этапа нет в Policy — предупреждение (переход в `recover`). Если процесс не найден или невалиден — «⚠ процесс «X» не найден / с ошибками» (D41).
- Колонка статуса показывает технический статус и живой lock (`runtime.json` + `project.lock.json`).
- Сортировка — по `updatedAt` по убыванию. Терминальные и отменённые задачи — в подменю.
- Если незавершённых задач нет, сразу открывается форма создания.
- Навигация: стрелки / `j` `k`, `Enter` — выбрать, `q` или `Esc` — выход.

### 3.1. Действия над выбранной задачей

`Enter` на задаче открывает подменю:

```text
AUTH-77 · Ожидание подтверждения плана · ждёт ответа

❯ Продолжить
  Показать статус
  Показать историю
  Отменить задачу
  Назад
```

### 3.2. Создание задачи

```text
Новая задача
Project root: /Users/user/Projects/cms   (git: main, чисто)

Ключ задачи: PAY-142
Название: Добавить оплату через СБП
Описание (Ctrl+D — завершить ввод):
> Нужно добавить СБП как способ оплаты на чекауте…
>

Начальный этап: Сбор и уточнение требований (agent: requirements)

❯ Создать и запустить
  Изменить
  Отмена
```

Ошибки ввода ключа (формат, дубликат без учёта регистра) показываются под полем, без выхода из формы.

Создание — один `commit` в новом каталоге: `state.json` (`phase = agent_pending`, `nextAgentInput = { kind: "initial" }`), `task.md`, `task.created`. Supervisor-сессия создаётся лениво при первом цикле: файл всё равно появится только с первым сообщением. После создания сразу запускается основной цикл.

### 3.3. Продолжение

```text
Продолжаем PAY-142 · Добавить оплату через СБП

Текущий этап:      Ревью
Последнее событие: 12:39 agent.settled — reviewer (attempt 2) отчитался
Следующее действие: supervisor проверит результат reviewer
```

«Следующее действие» вычисляется из `phase` и `trigger` (таблица в §6), а не из текста модели.

## 4. Экран выполнения (TTY)

### 4.1. Компоновка

```text
┌ PAY-142 · Ревью · agent: reviewer · attempt 2 ─────────────────── 00:03:42 ┐
  … прокручиваемая лента (Ink <Static>) …
  Проверяю изменения в payment_service.go…
  ▸ bash  go test ./...
  ✓ bash  (12.4s)
  ✗ отсутствует обработка timeout
  ▸ report_result
⠋ supervisor проверяет результат reviewer · 00:00:18
└ TEO: Ревью · supervisor · cycle 7 · in 41k out 3k · Ctrl+C — остановить ┘
```

- Шапка и подвал строятся из state и `RuntimeEvent`, а не из текста модели (раздел 20.1 исходной спецификации).
- Лента: завершённые строки уходят в `<Static>`, недописанная строка стрима — в динамическую область. Длинные строки переносятся, лента не обрезается.
- Вывод supervisor-а отображается в той же ленте с префиксом `supervisor ›` и приглушённым цветом.
- Thinking по умолчанию скрыт.
- Строка активности: спиннер, актор, текущее действие (`activity` из `runtime.json`), время в фазе.

### 4.2. Баннер перехода

Печатается в ленту после успешного `commit` перехода:

```text
════════════════════════════════════════════════════════════
✓ Реализация → Ревью
  Причина: тесты в контейнере проходят (run:01JB2X…), коммит 7baf12c на ветке
→ Запускаю agent: reviewer (attempt 2)
════════════════════════════════════════════════════════════
```

Для терминального этапа:

```text
════════════════════════════════════════════════════════════
✓ Задача PAY-142 достигла этапа «Готово к feature testing»
  Этапов пройдено: 7 · время: 2ч 14м · стоимость: $4.12
════════════════════════════════════════════════════════════
```

<a id="human-prompt"></a>

### 4.3. Human prompt

Описание и макет — [03-engine.md §6.3](03-engine.md#63-представление-вопроса).

Ввод свободного ответа: многострочный редактор. `Enter` — перевод строки, `Ctrl+D` — отправить, `Esc` — вернуться к вариантам. Перед отправкой — предпросмотр «Отправить ответ? (Enter / Esc)». Ответ попадает в журнал как доказательство, поэтому случайная отправка нежелательна.

Пока виден вопрос, поток модели на экране не обновляется: агент синхронно ждёт ответа в `ask_user`, а supervisor — в `human_pending`.

### 4.4. Клавиши во время выполнения

| Клавиша | Действие |
|---|---|
| `Ctrl+C` | Запрос остановки ([03-engine.md §9](03-engine.md#9-сигналы-и-остановка)) |
| `t` | Показать/скрыть thinking |
| `s` | Короткий статус задачи поверх ленты |

Ручное сообщение агенту во время хода (`steer`) — post-MVP: оно обходит supervisor, и для него нужно отдельное событие и правила.

<a id="wait-screen"></a>

### 4.5. Экран ожидания

Фаза `waiting` ([03-engine.md §12](03-engine.md#12-отложенная-перепроверка)):

```text
┌ CRM-12 · Код-ревью · agent: review_coordinator · attempt 1 ─────────── 02:41:10 ┐
  … лента …
  supervisor › schedule_recheck через 5 мин
════════════════════════════════════════════════════════════
⏳ Ожидание: ответ ревьюера в треде ревью и комментарии в MR
   Перепроверка в 15:40 (через 03:14) · ожидание 4 из 12 · всего ждём 17м
   Затем: review_coordinator проверит тред и MR
════════════════════════════════════════════════════════════
└ Enter — проверить сейчас · m — написать supervisor · q — выйти (ожидание сохранится) ┘
```

| Клавиша | Действие |
|---|---|
| `Enter` | Перепроверить сейчас: `wait.finished { reason: skipped_by_human }` |
| `m` | Сообщение supervisor-у (многострочный ввод, как в human prompt). Ожидание завершается, supervisor получает trigger `human_responded` |
| `q` | Выйти. State не меняется, lock освобождается, exit `6`. `teo resume` продолжит отсчёт |
| `Ctrl+C` | Остановка без подтверждения: агент не работает, прерывать нечего. `status = interrupted`, exit `130` |

Когда срок наступает, экран сам переходит к перепроверке. Терминальный bell не подаётся: человек не нужен.

## 5. Неинтерактивный режим

Включается, если `stdout` или `stdin` не TTY, или задан `--plain`.

```text
[2026-10-24T12:33:00Z][PAY-142][review][reviewer#2] started
[2026-10-24T12:33:04Z][PAY-142][review][reviewer#2] tool bash: go test ./...
[2026-10-24T12:33:16Z][PAY-142][review][reviewer#2] tool bash ok
[2026-10-24T12:39:00Z][PAY-142][review][reviewer#2] settled: reported_result
[2026-10-24T12:39:01Z][PAY-142][supervisor] cycle 7 started (agent_settled)
[2026-10-24T12:40:00Z][PAY-142][supervisor] decision transition_stage → fixing
[2026-10-24T12:40:00Z][PAY-142] transition review → fixing
```

- Текст модели печатается построчно с тем же префиксом (с `--quiet` — только события).
- Вопрос человеку: процесс печатает вопрос и завершается с exit `5`. Вопрос ждёт интерактивного `teo resume`. `ask_user` агента в этом режиме возвращает агенту ошибку ([04-agents.md §4.4](04-agents.md#44-ask_user)).
- Режим `confirm` при изменении Policy → exit `5`.
- Ожидание перепроверки: строка `waiting until 2026-10-24T12:40:00Z (30 min, 4/40): <waitingFor>`, затем раз в 10 минут `still waiting, 20 min left`. С `--no-wait` процесс не ждёт и выходит с exit `6`.
- Меню без аргументов недоступно: `teo` без TTY печатает список задач (как `status`) и подсказку с командами.

## 6. `teo status`

```text
PAY-142 · Добавить оплату через СБП
Project:  /Users/user/Projects/cms
Process:        dev

Stage:          Ревью (review)  · вход 12:33, 2 цикла
Status:         active · phase supervisor_running
Agent:          reviewer · attempt 2 · run 01JB2X… · settled: reported_result
Last event:     12:39:00 agent.settled
Last decision:  12:31 transition_stage implementation → review
Next action:    supervisor проверяет результат reviewer
Policy:         sha256:9b7e…41 (current)
Lock:           held by PID 18432 on macbook · heartbeat 3s ago
Usage:          in 412k · out 38k · $3.87
```

Таблица «Next action» по фазе:

| Phase | Текст |
|---|---|
| `agent_pending` | «запустить agent `<id>`» / «продолжить agent `<id>` по замечанию supervisor» / «перезапустить agent `<id>`» |
| `agent_running` | «agent `<id>` работает» (или «прерван — будет восстановлен» без lock) |
| `supervisor_pending` | «supervisor проверит результат `<agent>`» / «supervisor обработает ответ пользователя» / … по `trigger.kind` |
| `supervisor_running` | «supervisor принимает решение» |
| `decision_pending` | «применить решение `<action>`» |
| `human_pending` | «ждёт ответа пользователя: `<question, 80 символов>`» |
| `waiting` | «перепроверка в 15:40 (через 23 мин): `<waitingFor, 80 символов>`», а без живого процесса ещё и «`teo resume <KEY>` (`--now` — сразу)». Если срок прошёл: «перепроверка просрочена — начнётся при `teo resume <KEY>`» |
| `halted` | «завершена» / «заблокирована: `<reason>` — `teo resume <KEY>`» / «отменена» |

`--json` выводит объект `{ state, runtime, lock, policy: { currentHash, matches }, nextAction }`.

## 7. `teo doctor`

| Проверка | Уровень при провале |
|---|---|
| Node.js ≥ 22.19 | error |
| Каждый процесс `~/.pi/teo/<процесс>.md`: preflight, schema, граф, предупреждения; файлы с недопустимым именем | error / warning |
| Pi SDK загружается, версия | error |
| Все `modelRef` из Policy разрешаются, у провайдеров есть авторизация | error |
| Создаётся временная in-memory сессия (без вызова модели) | error |
| Project root определяется; права чтения и записи | error |
| `.teo/index.json` согласован с state-файлами | warning (`--fix`: перестроить) |
| Каждый `state.json` парсится и проходит инварианты | error по задаче |
| `events.jsonl`: целостность, outbox доставлен | warning (`--fix`: дописать outbox, обрезать хвост) |
| Ссылки state на существующие файлы сессий и runs | warning |
| Протухший lock / lock с живым PID / lock другого хоста | warning (`--fix`: снять протухший; чужой хост — только с явным подтверждением) |
| Осиротевшие `*.tmp` | info (`--fix`: удалить) |
| `.teo/.gitignore` на месте | info (`--fix`: создать) |

Вывод: по строке на проверку `✓ / ! / ✗`, затем сводка. Без `--fix` ничего не меняется.

## 8. Exit codes

| Код | Значение |
|---:|---|
| `0` | Команда выполнена; задача достигла терминального этапа; пользователь вышел из меню; задача отменена |
| `1` | Непредвиденная runtime-ошибка (баг, I/O) |
| `2` | Ошибка конфигурации: нет процессов, процесс задачи не найден или невалиден, модель не разрешается |
| `3` | Конфликт блокировки проекта или потеря lock |
| `4` | Задача не найдена или повреждена |
| `5` | **Новое.** Задача остановилась в нетерминальном состоянии и ждёт человека: `blocked`, `waiting_human`, неподтверждённое изменение Policy в неинтерактивном режиме |
| `6` | **Новое.** Задача ждёт срока отложенной перепроверки, человек не нужен: выход клавишей `q` или `resume --no-wait` до срока |
| `130` | Остановка через `Ctrl+C` |
| `143` | Остановка через `SIGTERM` / `SIGHUP` |

Коды `5` и `6` нужны автоматизации: `teo resume X` в скрипте должен отличать «готово», «нужен человек» и «ещё рано». Например, `teo resume X --no-wait --plain` из cron раз в 10 минут ведёт задачу без открытого терминала.

## 9. Формат сообщений об ошибках

Каждая ошибка отвечает на четыре вопроса из раздела 23 исходной спецификации:

```text
Task PAY-142 is blocked

What happened: supervisor ended 2 cycles without a control decision (SUPERVISOR_NO_DECISION).
Affected:      stage "Ревью", supervisor session sessions/supervisor.jsonl
Safe to continue: yes — no state was lost.
Next step:     teo resume PAY-142
```

Классы ошибок — в `src/errors/errors.ts`: `PolicyError` (2), `LockConflictError` (3), `TaskNotFoundError`, `TaskCorruptedError` (4), `StateVersionConflictError` (1), `ModelResolutionError` (2), `UserAbortError` (130). Неизвестные ошибки печатаются с stack trace только при `--verbose`; иначе — с путём к debug-логу `.teo/debug.log`.
